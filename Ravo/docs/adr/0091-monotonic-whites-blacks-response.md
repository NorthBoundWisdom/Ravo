# ADR-0091: Monotonic Whites and Blacks response

- Status: Accepted
- Date: 2026-08-30
- Extends: [ADR-0088](0088-lightroom-response-calibration.md),
  [ADR-0089](0089-exact-interactive-prefix-cache.md)

## Context

The first `ravo.core.whites` / `ravo.core.blacks` implementation treated both
controls as endpoints of one global affine transform:
`(sample - black) / (white - black)`. A positive Blacks edit therefore
subtracted a constant from every scene-linear channel. Lowering Exposure moved
otherwise valid colours below that constant, after which final RGB packing
correctly clamped the negative values to zero. The result was large, abrupt
black regions rather than a continuous dark-tone response.

This behavior was not part of the Lightroom endpoint evidence recorded by
ADR-0088. Static comparison with ART, RawTherapee, Filmulator, and vkdt also
supports keeping explicit exposure/black normalization separate from local
tone controls and applying localized tone response through luminance-derived,
hue-preserving factors. Those projects remain design references, not runtime
dependencies or pixel oracles.

## Decision

- Whites and Blacks operate on scene-linear working luminance around 18.42%
  grey. For `x = log2(Y / 0.1842)`, the white weight is
  `smoothstep(0, 4, x)` and the black weight is
  `1 - smoothstep(-8, 0, x)`.
- Whites reuse the calibrated Highlights endpoint strengths: +0.9 EV for a
  positive endpoint and -1.8 EV for a negative endpoint. Blacks reuse the
  Shadows strengths: +2.0 EV and -2.9 EV respectively. The output scale is
  `2^(white_ev * white_weight + black_ev * black_weight)` and the same positive
  scale multiplies R, G, and B.
- The envelopes meet at middle grey with zero value and zero slope. Across the
  full slider range, the minimum log-domain slope is 0.325 for Whites and
  0.625 for Blacks. Tone order therefore remains strictly increasing; a
  positive finite RGB sample cannot cross zero because of either control, and
  channel ratios remain unchanged.
- A contiguous canonical Highlights → Shadows → Whites → Blacks sequence
  executes in one row pass. Each control advances the per-pixel EV coordinate
  in recipe order, but the engine performs only one luminance logarithm, final
  exponent, and RGB multiplication. This is the same composition of monotonic
  maps without repeated full-image passes. The engine retains per-row
  cancellation and publishes only a complete owned result. Non-positive input
  created by an earlier explicit owner is preserved, not hidden by a fallback
  or output-stage repair.
- Preview contract v8 invalidates persisted pixels generated by the subtractive
  implementation. Recipe schema remains v1 because the stored slider intent
  and bounds do not change; this is a correction to their engine meaning.

## Consequences

Existing recipes with Whites or Blacks intentionally render differently.
Raised Blacks lifts only dark tones instead of subtracting a global black
point, and reduced Whites compresses only upper tones. Exact black remains
black, extended highlights remain available to the later Sigmoid/output owner,
and no additional clamp, gamut fallback, or alternate interactive algorithm is
introduced.

The response is a bounded Ravo extrapolation, not a claim of Lightroom pixel
equivalence. Future measured Whites/Blacks calibration may adjust the envelope
constants only with neutral and intermediate reference exports, while retaining
the positivity, monotonicity, common-RGB-scale, cancellation, and cache
invalidation gates established here.

## Rejected alternatives

- Clamp the affine result inside Whites/Blacks or at final output. That hides
  negative values but preserves the hard tone discontinuity and lost colour.
- Copy ART's explicit exposure black subtraction into the Blacks slider. Black
  normalization is a separate exposure owner and has different semantics.
- Apply independent per-channel toe curves. They can shift hue and create
  channel-specific clipping where a common luminance scale does not.
- Skip or approximate the controls during interactive preview. That would
  violate the exact-preview contract and produce a correction jump on settle.
