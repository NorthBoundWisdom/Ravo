# Ravo Repository Instructions

## Project scope

Ravo is the only buildable product: the C++20 Engine, the `ravo` CLI, and Ravo
Studio. The repository-root `CMakeLists.txt` builds only `Ravo/`. Darktable 0.9
is a historical reference only. Do not port unaccepted leftover IOPs
(ADR-0106). Frozen static fixtures live in `Ravo/tests/fixtures/frozen`.

`Ravo/` adds its own `AGENTS.md` constraints. `FreeCM/` is an independent
submodule. All `build/dependency_*` content is external source generated by the
parent-repository workflow and must not be treated as this repository's source.

## Engineering execution and delivery

- Fail fast by default: preserve real errors, structured failures, and explicit
  unsupported states. Do not hide ownership errors with silent fallbacks, empty
  catches, compatibility switches, or copied implementations.
- Update generated content only through its owning script. If generated output
  is wrong, fix the template or generator and regenerate; a manual edit to the
  generated output is not a final fix.
- Before changes across targets, dependencies, database schemas, threads, or
  product scope, provide a short plan that states ownership, lifecycle,
  error/cancellation paths, and the smallest validation set, then implement it.
- Delivery must describe behavior changes, key tradeoffs, validation actually
  run and its results, untested platforms, and whether a fallback was added. Do
  not describe an unrun check as passing.
- Execution TODOs contain only unfinished work, risks, dependencies,
  verification commands, and acceptance gates. Move durable conclusions into
  architecture, ADRs, code, or tests. When direction changes, remove stale
  references in the same change; do not retain two conflicting plans.

## Machine access to Ravo

- Repository agents must not use Computer Use for Ravo work. This includes
  accessibility automation, AppleScript/System Events, coordinate clicks or
  keystrokes, and application window screenshots used to inspect, operate, or
  validate Ravo Studio. Use Ravo's supported machine interfaces instead.
- When discovering a running Ravo process, resolve candidate executable paths
  and by default keep only processes whose executable is under the current
  repository root (for example, this checkout's `build/` or `install/`). Exclude
  same-named processes launched from sibling checkouts. If zero or multiple
  matching processes remain, report that state rather than choosing by launch
  time, foreground status, or other incidental activity. This identifies a
  process only; catalog and asset identity still follow the explicit rules
  below.
- Prefer the current-generation `ravo` CLI with `--json`. Resolve catalogs and
  assets with explicit identifiers, read recipe/history before a write, and
  read them back afterwards. Never guess a mutation target from the foreground
  window, process list, log tail, newest preview, or other incidental state.
- For visual Develop checks, use the read-only `catalog probe` path with strict
  `--set` overrides and a unique `--output <file.png>`, then inspect that image
  artifact directly. A generated preview PNG is acceptable evidence; a
  screenshot of the application is not a pixel or persistence oracle.
- If the CLI cannot expose state or intent needed by a task, extend the shared
  domain/services/command owner and the CLI instead of falling back to UI
  automation, direct SQLite access, QML introspection, or log scraping. Add a
  versioned JSON contract, structured failures, cancellation/conflict handling,
  and real CLI/service tests in the same change.
- Keep the machine-control contract transport-neutral. The CLI is the required
  baseline client and acceptance surface. MCP may be added only as a thin
  adapter over the same versioned C++ state/control contract; it must not own
  business state, image algorithms, SQL, command policy, or an MCP-only mutation
  path.
- Ephemeral live-window state belongs to the desktop C++ presenter/command
  layer, not QML or the catalog. Use `ravo studio sessions`, `state`, `develop`,
  or `preview` with `--json`; the live-session snapshot identifies Studio,
  catalog, selected asset set and state/selection revisions. Mutations must
  carry the observed asset and revisions, reject stale requests, and disappear
  cleanly when the window closes. Never infer the current selection from
  incidental process state.
- New or extended machine-visible image-result contracts should use bounded
  immutable bytes or no-replace temporary artifacts with MIME type, dimensions,
  color-profile identity, and content hash. CLI JSON should describe an output
  artifact; an MCP adapter may project the same result as an image resource
  without adding another renderer or cache owner.

More-specific implementation and validation rules for this boundary live in
[`Ravo/AGENTS.md`](Ravo/AGENTS.md).

## Before starting work

1. Run `git branch --show-current` and `git status --short --branch` to
   identify the current branch and preserve user changes.
2. Read the source files and documents directly relevant to the task; do not
   infer current behavior from upstream darktable habits.
3. For product/leftover boundaries, read `DevDocs/MIGRATION.md` first. For
   current product execution, then read [`DevDocs/TODO.md`](DevDocs/TODO.md).
   Three-platform package evidence is [`DevDocs/Packaging.md`](DevDocs/Packaging.md)
   and does not block other product work. Leftover algorithm ports are closed
   by ADR-0106. GPU remains deferred; policy lives in
   [`DevDocs/MIGRATION.md`](DevDocs/MIGRATION.md). Do not port OpenCL.
4. Before cross-layer changes, make ownership, lifecycle, thread boundaries,
   and the minimum validation set explicit.

Existing behavior is evidenced by Ravo code, tests, and frozen fixtures in
`Ravo/tests/fixtures/frozen`. `DevDocs/` contains live Ravo development
documents. `DevDocs/MIGRATION.md` defines leftovers. `DevDocs/TODO_*.md` files
define unfinished execution work.

## Ravo next-generation boundary

- The C++20 Ravo Engine, supported `ravo` CLI, and Ravo Studio share one
  service layer. `Ravo/README.md` records the currently accepted baseline;
  `DevDocs/TODO.md` owns unfinished product execution, `DevDocs/Packaging.md`
  records three-platform package evidence, and leftover algorithm ports are closed
  (ADR-0106).
- The `domain`, `services`, and Qt 6 Quick/QML `desktop` targets are already
  established. `Qt6::Qml`/`Qt6::Quick` and
  `QtQuick.Controls`/`QtQuick.Dialogs`/`QtQuick.Layouts` imports may only be
  used by desktop and its tests. Qt Sql/QSQLITE may only live in the private
  SQLite adapter; Qt Gui may be used in the private raster adapter for
  `QImageReader`. The first version introduces neither Qt Widgets nor a second
  UI architecture. QML may display state and forward intents only; SQL, codecs,
  image algorithms, business state, and task owners stay in C++
  domain/services/engine/adapters.
- Ravo production code must not depend on leftover darktable private headers,
  old libraries, dynamic IOPs, GTK types, or global `darktable` state.
  Validation uses Ravo tests and `Ravo/tests/fixtures/frozen`. Do not add a
  leftover tree, leftover CLI, or leftover test project.
- Before working in `Ravo/`, read `Ravo/AGENTS.md`, `DevDocs/ARCHITECTURE.md`,
  `DevDocs/MIGRATION.md`, and `DevDocs/TESTING.md`.

## Implementation principles

- First-party Ravo `.cpp` and production `.qml` files have a hard 2,000-line
  limit enforced by `configs/check_translation_unit_size.py` and
  `configs/check_qml_file_size.py`. Registered debt may shrink but never grow;
  remove its manifest entry in the same change that brings it within the limit.
  New split files target at most 1,500 lines. Do not move implementation into
  headers or `.inc` files to evade the checks.
- Test splits preserve ordered GoogleTest case identities, enabled state, and
  target membership through `configs/check_test_split_inventory.py`. Moving a
  test is not permission to rename, disable, or weaken it.
- This project has no default obligation to preserve darktable's historic
  plugins, Lua, old formats, or old UI ABI. Do not add empty shells,
  compatibility switches, or migration shims for explicitly removed
  capabilities.
- When Ravo decides not to support an old capability, record it as a leftover
  or dated product decision in `DevDocs/MIGRATION.md`. Do not add empty shells
  or leftover-faithful ports to inflate coverage.
- Do not replace 0.9 OpenCL with Metal inside the old application. A future
  Ravo GPU path is an Engine adapter only (`DevDocs/MIGRATION.md`); do not reuse
  the OpenCL API and do not add a silent CPU fallback.
- Follow the style of adjacent C/C++/CMake files and format only touched code.
  Do not bulk-format unrelated sources as part of another task.
- Record the rationale and validation method in the same change for new
  dependencies, public APIs, thread models, database schemas, and product-scope
  changes.
- Use `apply_patch` for manual source changes. Use generators and formatters
  only for output they explicitly own.

## Existing UI and core boundaries

- The GTK front end, dtgtk/Bauhaus, Lighttable, and Darkroom are not ported to
  Ravo, and the old UI receives no Ravo entry point. New capabilities are
  rewritten only in Ravo.
- Establish required behavior only through Ravo tests and frozen fixtures;
  do not run an independent leftover process.

## FreeCM and dependency source

- `.gitmodules` tracks `FreeCM/master`. To refresh FreeCM, first ensure that
  the parent repository and submodule have no unrelated changes, stay on the
  user's current parent branch, and run only
  `git submodule update --remote --checkout FreeCM` from the parent root. Do
  not create an agent update branch or run `git -C FreeCM pull` in the usually
  detached submodule. An unchanged gitlink is a silent no-op. When it changes,
  validate compatibility first; do not commit or push automatically without an
  explicit user request.
- The minimum checks after a FreeCM gitlink change are
  `python3 -m repomgrcpp.tools.repo_tool check-lock-compat --repo-root .`,
  `python3 FreeCM/tools/validate_repo_commands.py .`, read-only source-root
  checks, and Ravo configure/build on the current platform. Do not blindly
  stage a submodule checkout marked with `+` before explaining it.
- The ignored active `source_roots.lock.jsonc` is the primary source of truth
  for current checkout source roots. Before investigating dependencies, run
  `python configs/source_roots.py show --format json`, `resolve --format json`,
  and `verify`; never infer actual paths or modes from the committed template
  alone.
- `source_roots.lock.jsonc.in` is the version-controlled pinned baseline for
  direct dependencies. Permanent dependency, public CMake default, or
  source-root API changes modify only the template,
  `configs/source_roots.py`, and their CMake consumers. The root lock declares
  direct dependencies only; the transitive closure is resolved recursively from
  dependency templates in local seeds.
- `pinned` uses an exact commit. `latest` resolves only the newest commit
  locally visible in a seed. `manual` uses a real checkout for a non-empty
  `depsManualPath.<dependency>` and falls back to managed resolution when it is
  empty. `manual`/`latest` and machine paths belong only to the active lock and
  must not enter the release template.
- For dependency integration, do not modify
  `build/dependency_source_roots/*`. First switch the active lock to
  `depsMode=manual`, point the relevant `depsManualPath` at a developer-supplied
  real checkout (or an explicitly confirmed clean seed treated as a real
  repository), then run `python configs/source_root_workflow.py --update` and
  confirm wiring with `show`/`resolve`/`verify`.
- `python configs/source_root_workflow.py --init` is the only dependency step
  allowed to use the network, clone seeds, or prepare remote assets. `--update`
  must be fully offline: it reads the active lock and existing seeds, resolves
  and materializes the closure, and generates the root `CMakePresets.json`; it
  must not fetch, build dependencies, configure Ravo, or test Ravo implicitly.
- Day-to-day source-root diagnosis runs only read-only commands such as `show`,
  `resolve`, `verify`, `graph`, `audit`, and `policy-check`. Run a state-changing
  workflow only when the task explicitly covers initial preparation, dependency
  refresh, a lock switch, or materialization:
  - `--refreshpin` requires both active lock and template to be `pinned` and
    aligns dependency commits offline. It does not switch mode or materialize
    roots; run `--update` afterwards if needed.
  - `--pinlatest` selects `latest` only from commits locally visible in seeds
    and performs an offline update. The result is still a local candidate and
    cannot be published directly.
  - `--update` materializes source roots from the current active lock offline
    and regenerates host files.
  - `--cleanbuild --dry-run` lists conservative cleanup targets first. The real
    `--cleanbuild` removes build output only and preserves
    `build/dependency_seed_repos` and `build/dependency_source_roots`.
- A full dependency refresh starts with clean parent, FreeCM, and managed
  checkout worktrees, after saving a private snapshot of the active lock. Run
  networked `--init`, offline `--pinlatest`, a quick Ravo validation, remote SHA
  verification, template update, an explicit return of only the active lock
  mode to `pinned`, `--refreshpin`, `--update`, and another validation in that
  order. The `--pinlatest` CLI leaves the active lock in `latest`; if a
  candidate fails, do not modify the template. Restore the original active lock
  and materialized state with `--update`, then report the original failure.
- `configs/freecm.commands.jsonc` uses manifest v2: Config is explicit active
  context, and Build/Test/Run/Package bind only to a compatible Config rather
  than implicitly running Configure. After changing the manifest, run
  `python3 FreeCM/tools/validate_repo_commands.py .`.
- `source_roots.lock.jsonc`, `CMakePresets.json`, `.freecm/`, and
  `build/dependency_*` are local state and must not be committed or manually
  patched as a permanent solution. After an active-lock or manual-path change,
  run `--update` before configuring or compiling Ravo.
- Commit dependency repositories in topological order and push them first. Use
  `git ls-remote <remote> <published-ref>` to confirm the published branch or
  tag resolves to the target SHA, then update the parent template or gitlink.
  Never write a locally unpublished SHA into the template.
- Do not use FetchContent, CMake network downloads, replacement submodules,
  source copies, or generated-directory patches to bypass the workflow. See
  `DevDocs/Dependency_Workflow.md` for the complete integration procedure.

## Build and validation

The repository-root CMake builds only Ravo. FreeCM Config/Build/Run/Test use
`cmake --preset`, as do DwgParser and GeoDebugger.

For a newly prepared workspace, run:

```text
git submodule update --init FreeCM
python configs/source_root_workflow.py --init
python configs/source_root_workflow.py --update
```

After dependencies are prepared:

```text
cmake --preset mac_clang_debug -DBUILD_TESTING=ON
cmake --build --preset mac_clang_debug
```

Use `win_msvc_debug` / `win_msvc_release` on Windows and `linux_clang_*` on
Linux. `Ravo/tools/freecm_project.py` and `.ps1` are optional wrappers around
the same CMake commands, not FreeCM entry points.

For cross-platform builds, public headers, or platform branches, configure and
build Ravo with each available Windows, macOS, and Linux toolchain. When an
environment lacks a toolchain, run feasible static checks and report the
platform as untested; never describe one platform's result as passing on all
platforms. Run only Ravo's own unit/contract entry points.

Use validation proportional to risk:

- For Markdown or agent instructions, check links, commands, paths, and the
  diff; do not force a full compile.
- For CMake or dependency graphs, at minimum run offline `--update`, Ravo
  configure, and a build of the affected target.
- For C/C++ core, build the affected Ravo target. When the task requires
  behavior validation, run relevant Ravo unit/contract tests; for public
  headers or broad changes, run the full Ravo test suite.
- For CLI/services, validate structured errors, cancellation, output conflict,
  and resource destruction paths; do not start an old process as a live oracle.
- For catalog/import/desktop, validate schema create/reopen/migrate,
  transaction failure, duplicate import, corrupt/missing files, cancellation,
  atomic preview cache, late-result rejection, and resource destruction after
  window close. A manual UI result does not replace a service contract.
- For GPU work, follow `DevDocs/MIGRATION.md`: Engine adapter only, no OpenCL
  reuse, no silent CPU fallback, and a dated ADR before production code. Image
  algorithms still need Ravo unit/fixture validation.

When dependencies or test data are missing, perform all available static or
local checks first and accurately report what was not run and why; never call
“not run” a passing result.

## Documentation and generated files

- Documentation describes current ownership, invariants, failure behavior, and
  reproducible validation only. Do not append implementation diaries, per-run
  samples, completed checklists, or process already preserved by Git history.
- Keep one stable authority per topic: current capability in `Ravo/README.md`,
  architecture in `DevDocs/ARCHITECTURE.md`, migration/ledger/leftovers in
  `DevDocs/MIGRATION.md`, test policy in `DevDocs/TESTING.md`, unresolved
  cross-layer capability in `DevDocs/ProductRoadmap.md`, and the documentation
  index in `DevDocs/README.md`.
- Repository-owned development documents other than scoped `README.md` and
  `AGENTS.md` files live under `DevDocs/`. Execution TODOs use the name
  `DevDocs/TODO_<TOPIC>.md`. A TODO records only unfinished work, risk,
  dependencies, validation commands, and acceptance gates. Move durable
  conclusions into the stable authority before removing a completed item from
  its TODO.
- TODO/document renames are hard cuts: update every tracked reference and
  remove the old path in the same change. Do not leave redirects, compatibility
  copies, archived TODOs, or old-name placeholder files.
- When architecture, build commands, dependency conventions, or product scope
  change, update the owning document and `DevDocs/README.md` together. Do not
  create another overview for the same fact.
- Do not edit generated `CMakePresets.json` as a final fix. After changing a
  lock template or generator, run `--update`.
- Do not commit build trees, temporary reports, local active locks, IDE files,
  or dependency checkouts.
- Links must point to real repository files. When deleting or renaming a
  document, search the whole repository and repair references.

## Git and delivery

- When a user asks to commit (including “commit all diffs”), use the
  `review-and-commit` skill: Grok reads
  `.grok/skills/review-and-commit/SKILL.md`, and Codex reads
  `.codex/skills/review-and-commit/SKILL.md`. Do not commit from parent
  `git status` alone.
- If this change modifies a seed/source root (currently GeoControls or LibRaw),
  first commit and push that dependency repository to its remote default branch,
  confirm the SHA with `git ls-remote`, pin it in
  `source_roots.lock.jsonc.in`, and only then commit the parent repository.
  Do not commit the parent first, leave the seed only locally, or write an
  unpublished SHA into the template. Dependency push belongs to that commit
  workflow; the parent repository is still not pushed automatically.
- Commit-hook implementation belongs to `FreeCM/hooks/`. This repository owns
  only `hooks/path.ini.sample`, `hooks/install.py`, and `hooks/README.md`.
- After the first clone, create ignored `hooks/path.ini` and run
  `python3 hooks/install.py`. Pre-commit runs clang-format only on staged
  `Ravo/` C/C++; it formats QML/JS only when `qmlformat` is configured.
  `FreeCM/` is outside formatting scope.
- Use `[type]: description` commit subjects. Valid types are in
  `hooks/README.md`.
- Treat pure task-scope formatting changes made by hooks as expected output,
  not external dirt or a blocker. Re-stage and continue.
- Do not commit, amend, rebase, or push the parent repository without an
  explicit request.
- Before committing, check `git diff --check`, the full diff, and
  `git diff --cached`. Do not accidentally commit local locks, presets, build
  artifacts, secrets, or absolute personal paths.
- One commit should express one reversible intent.
- The delivery report lists results, main files, validation actually run, and
  remaining risks; do not present planned capability as implemented.
